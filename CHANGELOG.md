# Changelog

## 1.0, first release

- Prune an xgboost, LightGBM or YDF forest to the size you choose (a share, a count per class, or the smallest that passes your bar), compile it and check the compiled forest against the source library: `quickforest optimize`.
- Compile only, with no pruning: the compiled answers equal the library's (to the bit for xgboost; the bound per library is in LIMITS.md).
- A compiled forest is a flat file run by a small Rust library, or generated Rust code (`codegen-block`, `codegen-pgo`); `compile` and `optimize` build the fastest one the machine allows by default.
- Classification and regression, k-fold folders, LightGBM linear leaves and float64 answers; every command refuses what it cannot hold in one line.
- Tested by unit tests, a differential test over thousands of random models and a fuzz test of damaged files; what they found is listed under Development notes.

### Build defaults of the generated code

- Generated code builds at `opt-level` 3 (the chunks were 2; the driver's link already was 3) in the `fast` shape: no link-time optimisation, 16 codegen units per chunk (each chunk's trees are spread over modules so the units are real), and the profile-guided pass built in the same shape; `--shape top` (`options["shape"]`) is one codegen unit everywhere, chunks and driver, and no LTO across chunks. Why: a profile-guided build in one shape end to end ran faster than the other shapes compared on a text-feature preparation crate, [bench/README-GENERATED-SHAPE.md](bench/README-GENERATED-SHAPE.md); `test_codegen_target.BuildShapeTest`. The build plans its parallel `rustc` jobs against the free RAM (fewer jobs, then fewer units, then smaller chunks; one `RAM: building with N jobs / M units` line on stderr; `ram_mb` / `QF_RAM_MB` override; it never swaps and refuses in one line when one small job does not fit). Target: the PORTABLE CPU `x86-64-v2` (`generic` on arm; AVX is never compiled in by default). Building for the machine's own CPU is an opt-in, `--native` / `target_cpu="native"` (`--target-cpu CPU` names any other): the build only runs on that CPU type. The build writes its CPU features into the library and `CodegenForest` refuses, in one line and before loading it, a library built for features this CPU lacks: `test_codegen_target.TargetCpuTest`. Default, native and widest-CPU answers are bit-identical (same test, and the quick differential).
- A profile-guided build is checked on the rows it was profiled on: it refuses fewer than 2,048 rows and a profile whose two halves (two disjoint halves of the rows, profiled apart, then merged) agree on less than 82 % of the edge counts (`llvm-profdata overlap`). `best` (and `optimize`'s default) then builds `codegen-block` with a notice giving the row count or the figure, and `--backend codegen-pgo` fails in one line (`ProfileUnreliable`, exit 3). A small extra pass of the profile run covers the other ways the library is called (two threads, float64 answers, a base margin). A good build reports `profile_rows`, `profile_overlap` and `profile_function_overlap` (`optimize` prints them in `report.md`). The figures behind the two numbers are in LIMITS.md: `test_codegen_target.BestBackendTest`, `ProfileGateTest`, `test_profdata.FunctionOverlapTest`.
- `compile` and `optimize --compile` default to `--backend best`: `codegen-pgo` with `--data`, `codegen-block` without it (one notice line), `flat` only where `rustc` is missing, too little RAM is free or the model is beyond what generated code holds, and `codegen-block` where `llvm-profdata` is missing (a notice says why). `compile` writes `OUT.choice.json` so the loader comes from what was built, not from the suffix of `OUT`. `--backend codegen-pgo` asked for by name without `--data` still refuses: `test_codegen_target.BestBackendTest`.
- A profile-guided build applied a profile that did not match its code without a word (rustc exit 0; a function whose control flow changed lost its counts, and all but one of 37 did in a case seen): the build now fails in one line when a hot function (the fewest that hold 90 % of the profile's counts: the generated trees in practice) lost its profile or is not in the code, or the profile has no counts; warnings about cold functions are counted, not fatal: `test_codegen_target.ProfileGateTest`.
- `compile` with the default backend writes the kind of file it built whatever the output's name says (the loader is named in `OUT.choice.json`); when the name says the other kind (`OUT.flat` holding generated code, `OUT.so` holding the flat format) the notice line now says what the file holds and which `--backend` gives the other.

### Added

- `--keep auto` (optimize, prune; API keep="auto"): tries 5 %, 10 %, 25 %, 50 % (--keep-ladder) and keeps the smallest rung that passes the held-out bar, else the whole forest (exact, exit 0); one greedy run serves every rung. `--accept-any` (optimize) takes an explicit size whatever the figure (reported, not waived silently). README/REFERENCE show compile-only and prune-to-a-size as two first-class paths; the share and the count of --keep are documented with the rounding rule.
- `prune` and `optimize` record which trees of the original model they kept: `kept_indices` in `report.json` (also the dict `prune.run` returns), per model file a sorted list per output group and a flat list, as 0-based indices into the library's own tree list; `--keep 100%` lists every index: `test_structure.KeptIndicesTest`.
- `quickforest structure MODEL OUT.npz` and `structure.export(model)`: a model's trees as plain numpy arrays (child ids, features, float32 thresholds and leaf values, default direction, zero-as-missing flag, leaf ordinals, base margin and output kind) without running any prediction; categorical and linear-leaf models are refused with one line and exit 1: `test_structure`, and the `structure` rows of `test_input_matrix`.
- Every `predict` (flat family and generated code) uses all usable cores by default: `threads=None` is the number of CPUs the process may run on (capped at 64), from `evaluator.PARALLEL_MIN_ROWS` = 8,192 rows on (measured, REFERENCE "Threads") and one thread below; an integer still forces that many. `--threads` of `optimize`, `check` and `compare.py` takes `N` or `all` (default all); the bench scripts take a number (default 1). The answers are bit-identical for any thread count; `check --speed`, `compare.py` and the speed line of `optimize` time the library and the compiled forest on the same number of threads, every usable core by default (report keys `library_threads` and `compiled_threads`; `--threads 1` gives the one-thread figures). Tests: `test_pipeline` (`test_the_default_thread_count_is_every_usable_core_from_the_row_cutoff_on` and two more), `test_input_matrix` rows for `--threads`.
- `prune` (and `optimize`) of an xgboost `.json` / `.ubj` forest too big for `--memory-mb` (default 1500) reads it in a stream (`scripts/select_stream.py`): the file is scanned tree by tree, the selection rows are walked through the trees and one byte per tree and row names the leaf (in a file beyond half the budget), and the greedy selection keeps the same trees as the in-memory path. New options `--memory-mb`, `--scratch`, `--max-held-rows`, `--threads N|all`; `report.json` gets `models[i].scale` for a streamed model. 400,000 trees x 10,136 rows are pruned to ten in 23 minutes with a 162 MB peak on a 3 GB machine (table and limits in LIMITS.md): `tests/test_scale.py` (the same picks for every chunk size, block size and thread count; binary and 3-class; random forests and boosted; `.ubj` and `.json`).

## Development notes

What the tests found before the first release, and the corrections to the test harnesses.

### Bugs found and fixed by the release tests

Each fix has a pinning test that fails on the old code (named after the colon).

- YDF `--float32-sums` not bit-exact when a tree has more than 64 leaves: `test_f64.YdfF64Test.test_float32_sums_are_exact_for_trees_over_64_leaves`.
- LightGBM parser leaked `KeyError` / `IndexError` / `MemoryError` and hung on cyclic or shared children: `test_robust.LightGbmParserTest`.
- xgboost JSON parser leaked `KeyError`, accepted cycles, two parents and out-of-range children: `test_robust.XgboostParserTest`.
- `ARTIFACT.choice.json` could make `load_artifact` execute a Python file: `test_robust.DataAndChoiceFilesTest.test_a_choice_file_is_data_and_never_runs_a_file`.
- `load_data` ended a bad file in a bare `SystemExit`; it raises `ValueError` and the command-line tools print it as one line: `test_robust` (the cli-helper test).
- Evaluator API: NUL in a path, a `dtype` given as a string, `threads` of the wrong type or huge: `test_robust.EvaluatorApiTest.test_misuse_is_a_value_error`.
- Rust: opening a FIFO blocked forever; null and overflowing sizes in the C ABI: `EvaluatorApiTest` FIFO / directory and size-overflow tests, and the Rust mutation test.
- Model path errors (missing path, empty folder, unknown or mixed formats, a LightGBM file whose first line is damaged) ended in a bare `SystemExit`: they now raise `qf_formats.ModelFileError`, a `ValueError` for callers that is still a clean exit for the command-line tools: `test_robust.ModelPathErrorsTest`.
- xgboost `binary:logistic` / `reg:logistic` base score: the logit was computed with numpy's float32 `log`, which differs from the `logf` xgboost calls by one ulp for one score in six, so every row of such a model (with a base score other than 0.5) could be one ulp off: now the platform's `logf`: `test_f64.XgboostBaseMarginTest`.
- A process that loaded about a thousand copies of `libtreeflat` (every compiled model folder carries one) and predicted on several threads aborted with `fatal runtime error: out of TLS keys` (each copy that spawns a thread keeps one of the process's 1,024 pthread keys for good): copies of one build now share one loaded instance, `evaluator.load_lib`: `test_differential_pins.LibraryCopiesTest`. A process that loads a thousand DIFFERENT generated-code libraries is still bound by the same limit.
- xgboost `multi:softprob`: the float32 softmax summed its exponentials in float32, xgboost's `common::Softmax` sums them in a double and divides by that sum rounded to float32, so the answers were a few ulp off (3.6e-7 at 30 classes) while the code claimed xgboost's own operations: now the sum is a double in the one function the walker, the wave engines and the generated code share: `lib.rs f32_softmax_normaliser_is_summed_in_double`, `test_differential_pins.XgboostSoftmaxIsBitExactTest`.
- LightGBM binary with `sigmoid:s` other than 1 plus a base margin returned sigma(s * raw + margin) instead of sigma(s * (raw + margin)), 0.36 off in probability at s = 1.7, and the harness reference made the same mistake: the margin is now multiplied by s by every evaluator and by the reference: `test_readers.LightGBMTest.test_a_base_margin_is_added_to_the_raw_score_before_the_sigmoid_scale`. A forest of models with different `s` refuses a base margin: `test_a_base_margin_with_two_models_of_different_sigmoid_scales_is_refused_not_guessed`.
- `FlatForest.close()` while another thread was inside `predict()` freed and unmapped the forest under the running walk (SIGSEGV; ctypes drops the GIL): close now waits for the predictions in flight: `test_robust.EvaluatorApiTest.test_close_while_another_thread_predicts_waits_instead_of_crashing_the_process`.
- A FIFO given as the selection data file blocked for ever (the FIFO check covered model paths only): `test_robust.DataAndChoiceFilesTest.test_a_fifo_or_a_directory_as_the_data_file_is_refused_not_waited_on`.
- A truth `y` (or `fold`, `group`, `slice`, `eligible`) of shape (n, 1) broadcast against (n,): the regression bar took the MAE over n x n pairs and printed PASS for a pruned model that fails, `fold` counted 704,400 held-out rows out of 1,200: now an (n, 1) column is flattened and any other shape refused: `test_robust.DataAndChoiceFilesTest.test_the_optional_arrays_of_a_data_file_must_be_one_per_row` and `test_a_truth_column_gives_the_same_error_bar_verdict_as_a_flat_truth`.
- `prune` (the pruned model, `report.json`, `heldout_probs.npz`), `choose` (`ARTIFACT.choice.json`) and `optimize` (`report.json`, `report.md`) wrote through a symlink that sat where they write, outside the output folder; every output is now a new file renamed over the name: `test_robust.OutputFolderLinksTest`, `test_readers.YdfTest.test_prune_does_not_write_a_ydf_model_through_a_link_in_the_output_folder`.
- `compare.py` built no decision rule for a forest whose output transform is the identity, so a YDF random forest classifier's decision mismatches were never counted (a wrong answer still failed on max_err, but the report said 0 mismatches): it now decides by the task as `check.py` does: `test_pipeline.PipelineTest.test_compare_judges_the_decisions_of_a_ydf_random_forest_classifier`.
- An xgboost model trained with `gamma` > 0 and `tree_method="exact"` keeps the splits it dropped in the model's arrays (`num_deleted`), where no path reaches them: `compile` and `optimize --compile` crashed with an `IndexError`, and the reported node counts included the dead nodes. The reader now drops the unreachable nodes and counts only reachable ones; the differential and fuzz generators draw exact, approx and `gamma` too: `test_differential_pins.XgboostPrunedNodesTest`.
- `compile --backend codegen-pgo` and `optimize --compile --backend codegen-pgo` (documented as a profile pass over `--data`) refused with "needs options['pgo_rows']": only `--backend auto` and `compare` built the profile rows. `compile_model` now writes up to 20,000 rows of `--data` (a seeded random pick) as the profile and refuses with one line, "give --data", when there is none: `test_pipeline.PipelineTest.test_the_profile_guided_backend_takes_its_profile_rows_from_the_data_file_of_compile_and_optimize`.
- The regression bar and the held-out agreement bar were compared with the figures rounded for the report (4 and 3 decimals): a row 2.00004 % off passed "no row above 2 %", and 190,000 of 200,001 rows agreeing (94.9995 %, shown as 95.0) passed a 95 % bar. The verdict now uses the exact figures: `test_robust.BarsAreJudgedOnExactFiguresTest`.
- A bar given as NaN or infinite (`--min-agreement`, `--med-tol`, `--max-tol`, `--error-slack`, `--tol`) compared False with everything, so every model passed it; the command-line tools now refuse such a value and so do `RegBar` and `optimize()`: `test_robust.BarsAreJudgedOnExactFiguresTest.test_a_bar_that_is_not_a_finite_number_is_refused_by_every_entry_point`.
- An empty data file, a `.npy` that was not validated like the `.npz`, and an X of text ended in a numpy traceback (exit 1, the code of a failed check); `check` with no `--data` and `--random 0` tested nothing and printed PASS; `optimize --keep 100%` never read `--data` and skipped the `--regression` check: `test_robust.RefusedInputsTest`.
- Raw tracebacks on arguments that cannot work (each now one line naming the problem): `optimize --out` an existing file or under a file, `--backend` unknown (with or without `--compile`), `--decision threshold:abc`, `threshold:T` on a multiclass model, a rule file that is missing or fails to load, a FIFO or a device as the model path, `compile` and `prune` writing into a missing folder or onto a file, a negative `--random` of `check` and `compare`, `compare --speed-rows 0`: `test_robust.RefusedInputsTest`.
- The generated-code backends wrote their sources into `<output stem>-src` next to the output after deleting any folder of that name, so a folder of the user's with that name was removed without a warning. The sources now go into a folder the build creates in the system temp folder (`qf-codegen-XXXX`) and removes when it ends (`keep_src` copies them next to the output, as `<output stem>-src-XXXX`, and the result names that folder as `src_dir`): `test_pipeline.PipelineTest.test_generated_code_never_deletes_a_folder_that_was_there_before`.
- The verify bar (`check.run`, which `optimize --verify` runs) let an xgboost forest with a leaf 1e-5 off or a threshold one float32 step off pass, though the claim for xgboost is identical to the bit: xgboost without a base margin is now judged at difference 0, and a second set of rows (`paths`) reaches split nodes of every tree and falls on their threshold, a step below it and missing: `test_pipeline.PipelineTest.test_the_verify_bar_refuses_an_xgboost_forest_that_differs_from_the_library_by_one_part_in_100000`, `test_the_verify_bar_reaches_the_split_nodes_of_every_tree`, `test_path_rows_reach_a_sample_of_nodes_from_every_tree`.
- A named pipe (or a link to one) called `fold1.ubj` inside a folder of folds blocked `compile`, `prune` and `optimize` for ever: `test_robust.ModelPathErrorsTest.test_a_pipe_or_a_folder_named_like_a_model_in_a_fold_folder_is_not_a_fold`.
- `check --json`, `compare --md/--json` and the work files of `compare` were written through a symbolic link that sat in the output folder: `test_robust.OutputFolderLinksTest.test_check_and_compare_reports_and_work_files_are_not_written_through_a_link`.
- An xgboost model with `num_feature` 0 compiled without a word, and the generated code then aborted the process on the first prediction (a division by zero): every format refuses a model with no input features, and the generated `predict` returns code 1: `test_robust.XgboostParserTest.test_a_model_with_no_input_features_is_refused_by_every_format`.
- A folder name that is not valid UTF-8 made `compile` crash printing its result after the file was written, and `check` / `optimize` crash encoding the path: names are printed with a backslash escape and the model libraries' UTF-8 limit is one line: `test_robust.ModelPathErrorsTest.test_a_folder_name_that_is_not_utf8_ends_in_a_result_or_one_line_never_a_traceback`.
- The documentation and the `EngineRefused` message said the wave engines refuse anything compiled with `--f64-leaves` or `--float32-sums`; they refuse what the file's flags say (double sums, extended nodes, linear leaves), so an xgboost `--f64-leaves` file and a YDF `--float32-sums` file run: `test_f64.WaveEngineRefusalTest` (two tests and the message words).
- The README and `LIMITS.md` offered `apt install rustc cargo` for building the evaluator on aarch64 or an old glibc, but the Rust source needs rustc 1.88 (`rust-version` in `Cargo.toml` now says so; a distribution compiler of 1.75 fails); the generated code builds with an older one (`codegen-block` was built with rustc 1.75.0 on 2026-10-22, before the 1.0 build defaults).
- The "overfit" figure of `prune` subtracted the ensemble's held-out agreement from each model's own selection agreement when several models had no fold array; it now subtracts the models' own held-out agreement (`heldout.models_pct` in the report): `test_pipeline.PipelineTest.test_the_overfit_figure_compares_the_models_own_selection_and_held_out_agreement`.
- A selection data file whose X had another number of columns than the model ran silently (xgboost reads a missing column as missing, YDF ignores an extra one) or ended in the library's traceback (LightGBM, YDF): `prune`, `optimize` (also with `--keep 100%`), `check`, `compare` and `choose` now refuse it in one line naming both numbers, and so does every source's `predict` / `leaf_matrix`: `test_robust.ValidatedInputsTest.test_data_of_another_width_than_the_model_is_refused_in_one_line_by_every_command`.
- One NaN in the truth `y` made the regression error bar pass (`mae > mae` is False for NaN) and wrote `NaN` into `report.json`; NaN or infinity in `y`, `fold`, `group`, `slice`, `base_margin` and text in any of them are now refused by name, and a NaN can no longer pass a bar: `test_robust.ValidatedInputsTest.test_a_truth_or_index_array_holding_nan_or_infinity_is_refused_by_name`, `test_one_nan_in_the_truth_cannot_pass_the_regression_bar`.
- `--decision threshold:nan` (or `inf`) was accepted and made every decision the same class, so the agreement bar passed at 100 %: `test_robust.ValidatedInputsTest.test_a_decision_threshold_that_is_not_finite_is_refused`.
- A LightGBM text model with a wrong `tree_sizes` compiled, and `prune` / `check` then aborted the process (SIGABRT) when LightGBM loaded it; a short `feature_infos` or `feature_names` failed inside the library. The reader now compares `tree_sizes` with the trees it cut and the name and range lists with `max_feature_idx`; a LightGBM error at load is a `ValueError`; the fuzzer's text child also loads the file with the library and predicts a row: `test_robust.LightGbmParserTest.test_a_header_that_lightgbm_trusts_but_this_reader_ignored_is_refused`.
- A LightGBM text model with a NUL byte made `lightgbm.Booster` (and so `prune`, `check`, `optimize`) hang for ever, and a parameters block after the trees that was cut or had a damaged line killed it with SIGSEGV (found by making the fuzzer's text child load every file with the library too); text outside the trees that is not UTF-8 failed inside the library: all are refused when the file is read: `test_robust.LightGbmParserTest.test_a_damaged_tail_after_the_trees_is_refused_because_lightgbm_crashes_on_it`.
- YDF folds trained on the same features in another column order were averaged with swapped columns, and `check` passed because its reference mapped the columns the same way: `load_forest` refuses folds that disagree on the input feature names: `test_readers.YdfTest.test_folds_trained_on_the_same_features_in_another_column_order_are_refused`.
- A LightGBM threshold of exactly -3.4028235e38 sent the row -3.4028235e38 right (`floor32` turned it into -infinity), where LightGBM sends it left: `test_readers.LightGbmEdgeThresholdTest`.
- The error message of an evaluator that refused a file lost its reason (or raised `UnicodeDecodeError`) for a path of about 500 bytes or more: the buffer holds a 4,096-byte path and the reason, and is decoded leniently: `test_robust.EvaluatorApiTest.test_the_reason_a_file_is_refused_survives_a_path_of_hundreds_of_bytes`.
- `compare` and `compile --backend auto` judged an xgboost backend at 1e-6 where `check` and `--verify` demand identity to the bit, so a backend that drifted by 1e-7 would have been chosen as "exact": both use `check.bit_exact`: `test_pipeline.PipelineTest.test_compare_judges_an_xgboost_backend_at_difference_zero_like_check_does`.
- `compile` wrote a forest under a folder whose name is not valid UTF-8, which `check` and `optimize --verify` then could not open; `compile`, `choose` and `compare` refuse such an output path up front: `test_robust.ValidatedInputsTest.test_compile_refuses_an_output_path_that_is_not_utf8`.
- `compile MODEL MODEL` (and `choose`) replaced the model file by the compiled forest: the output may not be a model file of the run: `test_input_matrix` (output cells).
- A table of every command against every kind of damaged model, data array, artifact, output path and numeric option (`tests/test_input_matrix.py`, about 1,200 cells) found, besides the above: a truncated `.ubj` model crashed xgboost with SIGSEGV (a UBJSON object ends with `}`); an unreadable model file, a file name over 255 bytes and a `--json` / `--md` path in a missing folder ended in a traceback (the last after the whole run); `optimize --keep 100%` skipped the checks of `--sub`, `--seed` and `--decision`; infinity in X, a number beyond the float32 range in a float64 X, and xgboost's native backtrace in an error line; `--cases -1`, `--random 1000000000` (allocated for ever), `--cpu` of a CPU that does not exist, `--only` and `--opt` entries that mean nothing, a `--backend file.py` that is missing: each is now a refusal in the documented exit code and one line.
- An output path that is a symbolic link pointing at itself (`compile`, `choose`, `prune`, `optimize` without `--out`) ended in a Python traceback (`Path.resolve` raises on a link loop): the comparison with the model files now uses `os.path.realpath`, so `compile` replaces the link and `prune` refuses with one line: the `output is a link to itself` row of `test_input_matrix`.
- xgboost models trained on a DataFrame (they store feature names) can now be pruned, checked and verified: the prediction calls no longer validate names against the bare data matrix.
- A data file is read by what it holds, not by its name: .npy bytes under another name, or an .npz archive named .npy, no longer end in a traceback.
- In a data file, slice may hold only 0, 1 or -1, and fold, group and slice must be whole numbers (a 2 was a silently unused row, 0.7 was cut to 0, group ids 0.5 and 0.7 were merged).
- A --decision rule file is tried once when it is loaded and every answer is checked: an exception, a wrong shape, floats or NaN is one line. A rule that abstained with NaN used to score every abstained row as a disagreement. The shape the rule receives is documented.
- A LightGBM sigmoid:s that is not a finite number above zero is refused (LightGBM refuses it too); compile used to write a forest that answered 0.5 for every row.
- An xgboost model trained for zero rounds says "the model has no trees" instead of numpy's message.
- More than 1,024 output groups (classes) is refused at compile with the limit named; the file used to compile and then never open. Listed in LIMITS.
- A damaged YDF model folder (cut or missing node shard, missing files) is refused in one line instead of a traceback.
- Generated code: a categorical node with an empty category set sends every row right, as LightGBM does (it sent -1.5 left); the LightGBM reader refuses such a node.
- Generated code is built in a clean temp folder and only the library is copied to the output, so an output path with a % or a relative first part starting with - works; a failed rustc, linker or llvm-profdata run is one line, exit 3.
- Arrays numpy holds at an odd address are copied before they reach the Rust library (a misaligned slice is undefined behaviour there).
- quickforest --help, -h and help print the usage to stdout and exit 0.
- Docs: the fold number is the position in natural name order from 0; margin_scale is 1.0 for a LightGBM random forest; zero_missing uses float32(1e-35).
- A pruned xgboost model kept the original's `best_iteration` and `best_score`: the scikit-learn wrapper's predict (rounds 0 to best_iteration) raised "Out of range for tree layers" on a pruned file with fewer rounds, or silently used a prefix of the kept rounds (0.24 off in probability), a third model that neither the held-out agreement nor `--verify` had measured. A pruned file carries none of `best_iteration`, `best_score`, `best_ntree_limit`: `test_written_files.XgboostFilesTest.test_every_pruned_xgboost_file_predicts_like_the_pruned_forest_through_booster_predict` and `..._through_the_scikit_learn_wrapper`. A pruned LightGBM file now lists the importances of the trees it holds (`qf_lgb.importance_tail`): `LightgbmFilesTest`; a pruned YDF folder still keeps the original's `validation_loss` and training logs (the `ydf` API cannot edit them), which REFERENCE.md says.
- A pruned xgboost file renamed a feature that has a non-ASCII letter: the JSON was written with `\u` escapes, which xgboost's reader keeps as six characters, so predicting with the DataFrame's own names failed with a feature-names mismatch. The file is written as raw UTF-8: same test, feature names with an accented letter.
- `optimize --compile` wrote the path of its work folder (`_work/model.flat`) into `report.json` and then moved the folder; a run refused after the compile named an artifact it had deleted. The report names the file where it is, or none: `test_written_files.XgboostFilesTest.test_every_path_a_report_names_exists`.

### Corrections to the test harnesses (the product was right)

- Page-release test (`test_scale`): on the CI runners the model file stayed 2.0 to 2.2 MB of 4.3 to 4.4 MB resident, against a bar of 0.62 MB, on every job. `tests/diag_pages.py` showed the cause on GitHub's runners (Linux 6.17, ext4, x86-64 and aarch64): a file written in one write sits in 2 MB folios of the page cache, and one page fault maps all of one (2,048 KB, `FilePmdMapped` 2,048 kB in smaps), where a file written in 1 MB pieces, or read back from disk, maps 64 KB; `madvise(MADV_DONTNEED)` splits that mapping and the next fault maps the 2 MB again, so the resident set could not go under 2 MB whatever the release window. The bar came from a probe that wrote its file in 1 MB pieces (64 KB). The probe now measures the model file itself, in the mapping the product makes, and the test prints which stretches of the file were resident at the peak when it fails; CI runs `tests/diag_pages.py` before the unit tests. The mapping asks for small pages (`MADV_NOHUGEPAGE`): the same run keeps at most 0.42 MB resident; pinned by `test_scale.ScaleTest.test_the_model_file_is_mapped_without_huge_pages`.
- Differential harness: every generated-code case (`--codegen-every`, `--pgo-every`) was a YDF case, because the pick `case % N == N - 1` and the format `case % 3` aligned for every N that is a multiple of 3 (all the defaults). The pick now rotates over the three formats: `test_differential_pins.CodegenPlanCoversEveryFormatTest`.
- Rust tests: planting one change in the loader's bound checks (thirteen of them) or in the extended-node walker survived `cargo test`; each bound is now tested at its first value past the edge, and the categorical, zero-as-missing and default-direction paths at their edges (`each_bound_of_the_loader_refuses_the_first_value_past_it`, `extended_nodes_follow_lightgbm_at_their_edges`).
